# Design decisions and trade-offs

These describe current choices, not architecture added by documentation. [Architecture](architecture.md) shows their boundaries.

| Decision | Why / advantage | Cost or limit | Alternative / future option |
|---|---|---|---|
| PostgreSQL idempotency, not Redis | Uniqueness and payment/event intent commit atomically; survives cache expiry. | DB reads, contention and retention growth. | Redis can accelerate lookup but should not replace durable correctness without a different durability design. |
| Transactional outbox, not direct publication | Closes DB commit/send failure gap with local atomicity. | Polling delay, DB scans, duplicate delivery and failed-row operations. | CDC/Debezium; still requires consumer deduplication. |
| Kafka lifecycle processing | Decouples acceptance from provider work, durable replay/partition ordering. | Broker operations, lag, rebalances, DLT and event evolution. | A DB queue is simpler at small scale; another broker needs equivalent delivery design. |
| Redis cache and Lua limiter | Low-latency shared cache and atomic merchant admission across replicas. | Ephemeral dependency; cache staleness and fail-closed new creation when coordination is lost. | PostgreSQL-only reads/limiter, trading latency/DB work; managed Redis changes operations, not business guarantees. |
| paymentId as payment Kafka key | Orders a payment's events within its topic partition. | Hot aggregate stays serial; partition count bounds active consumers. | Different shard keys require explicit ordering reconstruction. Refund events currently key by refundId in a separate topic. |
| Mock HTTP providers | Exercise sockets, HTTP errors, deadlines, signatures, durable external ledgers and ambiguous results reproducibly. | No real network/payment/settlement fidelity; mocks share JVM/VM locally. | Real sandbox/provider adapters with contract and retention validation. |
| Retry outside circuit breaker | Every permitted physical attempt is checked by its provider circuit and recorded. | Retries amplify traffic; circuits are local per JVM, not distributed health consensus. | Queue/backoff policies or provider-wide admission, requiring measured demand. |
| Restricted failover | Fallback only when no earlier ambiguous attempt may have charged. Business decline is terminal. | Less apparent availability during uncertainty. | Blind fallback is unsafe; real provider guarantees may permit additional carefully classified cases. |
| PENDING_CONFIRMATION | Preserves unknown external result instead of assuming timeout means failure. | More states, reconciliation load and manual unresolved cases. | Synchronous certainty is impossible under response loss without external outcome recovery. |
| Original-provider refunds | Refund targets the provider transaction that actually charged. | A failing original provider delays refunds; no payment-provider fallback. | Provider-specific reversal/settlement workflows after real integration. |
| Saga-style compensation, not XA/2PC | Durable idempotent refund command reverses business effect without distributed locks. | Compensation can fail/be pending; not an atomic rollback or general Saga engine. | 2PC only across participants that support it; HTTP payment providers do not participate here. |
| Merchant API keys | Straightforward server-to-server principal and tenant isolation with peppered digests. | Key lifecycle/rotation responsibility; no user identity federation. | OAuth client credentials/external IAM if requirements justify it. |
| Prometheus and OTEL | Bounded metrics, operational signals and cross-boundary tracing aid diagnosis. | Sampling/export overhead and cardinality discipline; local debug exporter has no durable trace store. | Managed telemetry backend and tuned sampling after measurement. |
| Kubernetes replicas/HPA/PDB | Deployment lifecycle, probes, disruption controls and resource-based scaling configuration. | Cluster complexity; DB/provider/partition budgets and startup limits remain. | Compose for local simplicity; managed platform/lag-based autoscaling as future design. |
| Offset pagination | Straightforward totals and deterministic sorting. | COUNT/large offsets grow expensive; pages can shift as data changes. | Cursor pagination; current small plans did not justify adding it in Step 15. |
| Coalesced last-used telemetry | Reduces concurrent writes to one API-key row while keeping fresh authentication. | Timestamp approximate up to interval; JDBC UPDATE still runs per request. | Per-request audit with cost, or separately designed asynchronous telemetry. |
| Local PG burst CPU headroom | One paired experiment reduced throttling and mixed p95; request/memory unchanged. | More potential CPU competition; results are one local sample. | Remeasure production query/memory/CPU budgets before sizing. |

## Realistic future roadmap (not implemented)

Real provider sandbox integrations and settlement/dispute models come first with contract/idempotency validation. Operational priorities include an external secret manager, managed HA PostgreSQL/Redis/Kafka, backup/restore exercises, DLT/failed-outbox replay tools and an admin reconciliation console. CDC can reduce polling work after operating maturity; processed-event/outbox archiving needs a replay-aware retention policy. Cursor pagination and KEDA/custom lag-based scaling depend on demonstrated need. A local merchant presentation dashboard now exists; an administrative console remains future work. Multi-region/sharding require a new ownership/consistency design, not additional YAML alone. No future item should be listed as current functionality.
